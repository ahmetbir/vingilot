## The design, in one paragraph

A dark, focused workbench. The window is one gradient ground (five selectable
sidebar washes: buzz/graphite/slate/ember/ink; five accents:
ember/orange/mauve/teal/green — ember `#e0a35f` default) on which three
rounded cards float: the **stage** (center), the **dock** (right, or bottom
drawer, or floating — ⌘\\), and the **status bar**. Left of the stage sits the
sidebar (resizable 196–340px): Inbox / Agents / Pull requests / Deck nav rows,
then Projects (with worktree children + run-state dots), Channels, Direct
messages, and a me-footer. The stage hosts four views (⌘1–⌘3 + PRs): **Deck**
(tasks strip + terminal), **Agents** (card grid with live model/token/cost),
**Inbox** (mentions), **Pull requests** (list + timeline detail with merge
box). The dock has six tabs: Crew (channel chat), Diff, Files (tree +
right-click menu), Checks, History (graph/reflog), Run (dev server + docker
services). Typography: Inter for UI, JetBrains Mono for everything monospace.
Fonts ship in-app (no CDN — the mockup's Google Fonts link is mockup-only).

## Key decisions (owner-confirmed or consciously taken)

1. **Dark-first, dark-only shell — but the Theme style gallery survives**
   (owner, 2026-08-29, on the Settings screenshot: "bunlari kullanalim ama
   ya — gecersiz olmus bu kisim"). Force-dark means: pin the resolved theme
   to the DARK member of the selected theme's pair, not to buzz-dark
   unconditionally. The 60-theme Theme style picker keeps working (dark
   variants only); the Vingilot shell palette seeds specifically the default
   buzz-dark; other themes derive their own colors as they always did. The
   wash overlay rides on any theme; the Vingilot accent applies to the Buzz
   themes (non-Buzz themes keep their own accent picker). The now-invalid
   "Color mode" row (System/Light/Dark) reduces honestly to Dark — no dead
   buttons. Old light code paths stay compiled but unreachable.
2. **Status-bar quick actions are configurable canned prompts** (owner,
   verbatim intent): each button = label + prompt template, editable in
   Settings; pressing it types the prompt into the active tmux pane and hits
   Enter. Defaults: Stop, Commit, Create PR. **Review is the exception**: it
   dispatches a task to an external agent — which agent is itself
   configurable — via the Review popover (reviewer picker + instruction
   textarea, both persisted). Review never types into tmux.
3. **Terminal gains splits** (owner: "terminali ikiye bolmeli suruklemeli").
   Split horizontal/vertical inside one tab, draggable divider, DnD (files
   from Finder, text) targets each half independently — extends the existing
   `vingilot_drop` + `nativeDrop.ts` routing.
4. **Terminal scroll bug is in scope** (owner: "scroll duzgun calismiyor") —
   diagnose against the real app first (systematic debugging, not a guess),
   fix rides with Phase 2.
5. **Catppuccin exits.** The inventory proved --primary is stock Catppuccin
   mauve to the bit. The new token layer replaces it; mauve survives only as
   one of the five accent choices (a nod, not a base).
6. **Old chrome is replaced, not themed.** AppSidebar's accordion,
   ProjectStatusBar/ChatStatusBar, TerminalTabStrip get successors, not
   restyles. Their vocabulary (quiet plates, honest doors, lead/name
   truncation, git-letter colors, AttentionDot semantics) carries into the
   successors — the words and semantics were audited good; the material was
   not.

## P4.2 — selection belongs to content, not to chrome (owner, 2026-08-31)

His screenshot: one stray drag selected the ENTIRE app — sidebar rows, tab
labels, project names, the file viewer's line-number gutter, the status bar.
His rule: "secme kismi sadece dosya olmali ya da terminal ici. dosya satir
numaralari filan secilemez olmali."

So: the shell is `user-select: none` by default, and text selection is
OPTED INTO by exactly the surfaces whose content is meant to be copied —
- a file view's CONTENT (never its line-number gutter),
- a diff's code lines (never the gutter, never the +/− markers' column),
- the terminal (xterm owns its own selection already — do not fight it),
- message/chat bodies and code blocks in them,
- inputs and textareas (they select natively; do not break them).
Everything else — nav rows, tab strips, section headers, status bar,
buttons, tree rows, chips — must not select. Keyboard accessibility and
focus rings are untouched: this is about pointer drags, not about reachability.
Implementation note: put the default on the app root, opt in on the content
containers; verify by dragging across the whole window in a spec (a real
pointer drag, then read `window.getSelection()` — it must be empty over
chrome and non-empty over a file's text).

## P4.4 — the diff stops looking like terminal output (owner, 2026-08-31)

"diff ui'i artik guzel olsun bi tik yaaa hala cok terminal gibi." His
screenshot shows raw `git diff` text pasted into a pane: the `diff --git`
line, the `index 4dc47…` line, `---`/`+++`, `@@` hunk headers and the

badly, with the file path repeated inside the body.

What it must become (mockup .frow/.hunk/.dline vocabulary, Vingilot.html

- **Drop the plumbing.** `diff --git`, `index`, `---`, `+++` are git's wire
  format, not information — the file row above already says which file. The
  `@@` header becomes the mockup's quiet `.hunk` strip with the human part
  of the header (the enclosing function) kept when git gives it.
- **A gutter, not a prefix.** Old/new line numbers in their own narrow
  columns (the mockup's `.dno`), the +/− carried by the row's tint and a

- **Real code colour.** The app already ships Shiki (the file viewer uses
  it): highlight the diff's code by language, over the add/remove tint,
  instead of a flat green/red wall.
- **Per-file structure**: the file row (path lead/name, +N −N, change square)
  stays the header for its hunks; long files collapse.
- Selection rule from P4.2 applies: code lines selectable, gutter not.

Applies to every diff surface the redesign owns — the dock's Diff tab, the
History commit patch, and the full-width diff tab from P4.1 item 3.

## P4.3a — the dock History panel hangs forever (diagnosed 2026-08-31)

Owner, live: the full-width History TAB renders correctly ("all branches ·
200+ commits", subjects, chips, lanes) while the DOCK panel sits on
"reading this repository's history…" forever, header reading "first-parent".

ROOT CAUSE, read from the code (DockHistoryPanel.tsx, the first-parent
effect): the effect lists `trunk` in its dependency array AND calls
`setTrunk(READING)` as its first act, while its cleanup sets `alive = false`.
So: trunk is null → effect runs → setTrunk(READING) → trunk changed → cleanup
fires and kills the in-flight read's continuation → effect re-runs → the
`trunk !== null` guard returns early → nothing ever completes. The panel is
structurally incapable of leaving READING.

FIX: drop `trunk` from the dependency array (deps become `[cwd, scope]`) and
drop the `trunk !== null` guard — re-reading when the worktree or the scope
genuinely changes is correct, and the current shape is a self-cancelling
loop. Then add the spec my P4.3 brief already demanded: render the DOCK
panel against this repository's real history and assert ROWS APPEAR — the
full-width tab passing must never again stand in for the panel.

Also record the rule this breaks: a panel must always reach a terminal state
— rows, an honest empty sentence, or an honest refusal. A permanent
"reading…" is the one outcome that is never acceptable.

## Vocabulary: three different things are called "split" (owner, 2026-08-31)

"split ile unified farkli ama" — the word is overloaded three ways and they
must never be conflated in code, copy, chords or tests:

1. **Terminal split** (P2, `lib/terminalSplit.ts`, ⌘D / ⇧⌘D) — TWO PTYS
   inside ONE tab, with a divider. About shells.
2. **Diff Split/Unified** (P4.6, `data-dvm`, the `.dvseg` control) — a
   RENDERING MODE of one patch: side-by-side columns vs one inline column.
   Nothing is split in the layout; no second tab, no second pane, no second
   pty. It is the diff viewer's own toggle and belongs only to it.
3. **Tab split** (P4.7) — TWO TABS sharing the stage, each drawing whatever
   it draws, with a divider between them.

Rules that follow: the diff's Split button must never move a tab or create a
pane; the tab split must never be labelled "unified"; and a diff rendered in
Split mode inside a tab that is itself in a tab split is a legal, ordinary
state — three dividers on screen, three different meanings, each named for
what it actually does.

## P4.7 — the tab strip earns VS Code's manners (owner, 2026-08-31)

"cmd w ye filan basinca tab kapanmali. iki tab yan yana acabilmeliyim filan.
vscodedaki seyler lazim shortcut ve drag."

The strip now holds shells AND view tabs (files, commits, diffs), so it has
to behave like an editor's tab bar, not a terminal's:

1. **⌘W closes the focused tab.** Today ⇧⌘W closes a terminal tab and ⌘W is
   the app's own close-window (queue item #25 from long ago: app_menu.rs
   dropped close_window). Make ⌘W the tab close — for a view tab it closes
   the reading, for a shell it ends the session with the confirmation that
   act already carries. Audit the chord across every claimant first (the
   fork's six-claimant idiom), and keep a way to close the window.
2. **Two tabs side by side.** Split the STAGE between two tabs, the way a
   terminal is already split within one — a view tab and a shell, or two
   view tabs, sharing the stage with a draggable divider. This is distinct
   from P2's terminal split (two ptys inside one tab); both must survive.
   ⌘\ is taken (dock float), so pick from VS Code's own: ⌥⌘← / ⌥⌘→ are
   already tab navigation here, so the split door needs a fresh chord plus
   a palette row and a tab context-menu item.
3. **Drag to reorder, drag to split.** Dragging a tab within the strip
   reorders it; dragging it onto the other half of a split moves it there;
   dragging it out over the stage's edge starts a split. HTML5 drag is
   already in this app (`SidebarDndContext` for channel sections) — reuse
   that vocabulary rather than inventing a second one.
4. **The rest of VS Code's tab manners**: ⌘1…⌘9 already select — keep;
   middle-click closes; a context menu with Close, Close others, Close to
   the right, Split, Copy path; and the strip scrolls without losing the
   active tab (it already does).

Scratch stays unclosable-by-rename but IS closable; a shell's close keeps
whatever confirmation it has today. Nothing here may disturb a live pty:
the P2 rule stands — reordering or splitting a tab must never reattach,
resize or end a terminal it did not close.

## P4.8 — the diff's Split mode is a lesser citizen (owner, 2026-08-31)

"diff split te unified'dan farkli da neyse bi sonrakine artik" — noticed and
deferred by him, so it is queued rather than urgent, but it is a real gap:
P4.6 shipped Split as a second-class rendering. From that round's own
deferred list, Split lacks what Unified has —

- **word-level highlight** (`.wd`): Unified marks the changed tokens; Split
  does not, so the reader loses exactly the thing the side-by-side layout is
  supposed to make easier to compare.
- **the comment affordance** (`.addbtn` on hover) and therefore no way to
  start a note on a line while reading side by side.
- **inline review threads** (`.rvw`): a crew note anchored to a line does not
  render in Split at all, so the same diff shows different information
  depending on a toggle that is supposed to be only about layout.
- **row windowing**: Unified virtualizes over its exact 22px rows; Split's
  paired rows have unknowable heights, so a large patch renders whole.

AND IT IS ALSO A VISUAL BREAK, not only a feature gap ("ui olarak ta
farkli", with both modes screenshotted side by side). From those shots:

- **Split wraps where Unified does not**, so its rows are two and three
  lines tall and the two columns stop lining up — the one thing a
  side-by-side diff exists to do. Wrapping must either be off in Split (with
  horizontal scroll shared by both columns) or applied to BOTH sides of a
  pair so a wrapped row grows on both.
- **The gutters are drawn differently.** Unified's numbers are the generated
  content of one hanging-indent block; Split renders them as its own inline
  spans, so column widths, colour and alignment do not match.
- **Filler rows read as holes** — a deleted-side gap is a large blank block
  rather than the quiet hatched band a reader can skim past.
- Row height, tint, the inset edge and the hunk strip should be the same
  vocabulary in both; today they visibly are not.

The rule this breaks is worth naming: **a rendering mode may change the
shape of the information, never its content — and never its vocabulary.**
Whatever a reader can see, mark, comment on or be shown in Unified must be
available in Split, drawn in the same language, with the pair aligned.

Fix shape: lift the row decoration (word markup, affordance, thread anchor)
out of `PatchUnified` into something both layouts consume, and give Split a
measured-height windowing pass (or an honest "large patch renders whole"
note if measurement proves worse than the long DOM — but measure first).
