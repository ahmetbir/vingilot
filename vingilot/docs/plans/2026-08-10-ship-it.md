# Ship it — a name, a build, and a way to answer back

> **For agentic workers:** implement task-by-task. Steps use checkbox (`- [ ]`) syntax.
> **Branch:** `vingilot/ship-it` off `vingilot/team-thread-fidelity`, in a separate git worktree at `/Users/ahmetyusufbirinci/self-hosted/vingilot-brand` (the main checkout is busy with `vingilot/dashboards`). Merge order is dashboards first, then this.

**Goal:** The owner wants to start using this on his work machine, and to have somewhere to
put what he finds when he does:

> *"kanka bunu deploy edelim artık, iş bilgisayarında kullanmaya başlamak istiyorum. ve bi
> mekanizma kurmamız lazım, feedback için… bence bunu public bi repoya pushlayalım. bi tane
> de action yazalım, dmg çıkarsın."*

**Three facts settled before this plan, so nobody re-derives them:**

1. **The relay is stock.** Against `upstream/main` the fork is 288 files, 63,846 insertions
   and **114 deletions**, with `crates/`, `migrations/`, `web/` and `mobile/` at zero diff.
   So the app connects to his existing relay unchanged — nothing is deployed server-side.
2. **A macOS `.dmg` cannot be built on Linux**, so his Hetzner runner is out for this job.
   GitHub's `macos-latest` runners are free and unmetered on public repositories, which is
   what makes the public push worth doing on its own terms.
3. **The repo is safe to publish.** Licence is Apache 2.0 (attribution preserved). A scan of
   tracked files and of all 161 fork commits found no keys, no tokens, no personal paths and
   no relay hostnames — every `nsec1…`/`npub1…` hit is an upstream doc placeholder. The plan
   documents do quote the owner verbatim in Turkish; that is a record of why the product is
   shaped as it is, and it stays unless he says otherwise.

## Task 1 — The name and the mark

The app is a fork with its own product identity. It should say so, and it must be able to sit
in the Dock beside his existing Buzz without either one shadowing the other.

- [ ] **Read first, report before changing:** every place the product is named or drawn —
      `desktop/src-tauri/tauri.conf.json` (productName, identifier, window titles), the icon
      set under `desktop/src-tauri/icons/`, `desktop/src/shared/ui/buzz-logo/**`
      (`BuzzMark.tsx`, `FuzzyLogo.tsx`, `BuzzLogoAnimation.tsx`, `FlappingBee.tsx`,
      `buzz-logo-animation.css`), and every consumer of those components (App.tsx's cold-boot
      gate, TurnLivenessIndicator, AgentSessionTranscriptList, BackupStep). Report the list.
- [ ] A distinct bundle identifier and product name, so both apps install and run at once.
      **Say what this does to existing app-data and keychain entries** — a new identifier
      means a new app-data directory, and the owner must not silently lose his workspace
      layout, notes, or agent keys. If a migration is needed, it is part of this task; if the
      honest answer is "his existing Buzz install is untouched and Vingilot starts empty",
      that is fine but it must be *stated*, not discovered.
- [ ] The mark: prepared assets are in the session scratchpad, derived from the owner's own
      artwork by keying luminance to alpha — a tight key that drops the source's glow,
      because at low alpha the glow reads as a grey smudge on a light background.
      **Both themes must work.** The existing `BuzzMark` is an SVG tinted by `currentColor`;
      match that mechanism (a CSS mask over `currentColor` does it for a raster) rather than
      shipping a white-only bitmap that vanishes in the light theme.
- [ ] The app icon set is generated, not hand-cropped — `cargo tauri icon` from one square
      source produces every size plus `.icns` and `.ico`. Check the result at 16px: a mark
      that is unreadable in the menu bar is a mark that failed.
- [ ] Upstream's bee is not deleted where it is upstream's to draw. Anything under
      `shared/ui/**` that other upstream surfaces render needs a seam entry with a real
      reason, or a fork-owned component beside it. Decide and say which.

## Task 2 — The loading animation

- [ ] The owner's clip is white-on-black, 1764×1176, 5.04 s, 121 frames, and the mark
      breathes — sails and waves move. Because it is white on black, alpha is luminance and
      the key is clean; no chroma work is needed.
- [ ] Deliver it at a size that suits a loading surface, not the source resolution. State the

- [ ] **Both themes, again.** An animated mask tinted by `currentColor` is the ideal; if

      is not ready, the gate renders the static mark — never an empty box.
- [ ] Audio: the source carries an audio track. It goes.

## Task 3 — The build that produces a `.dmg`

- [ ] A workflow that builds the desktop app on `macos-latest` and attaches a `.dmg` to a
      GitHub Release on a tag push. **Read `.github/workflows/desktop-release-candidate.yml`
      and `signed-macos-canary.yml` first** — upstream already builds this app on macOS, and
      the useful parts (toolchain setup, hermit activation, pnpm cache, tauri build
      invocation) should be reused rather than reinvented. Report what you took.
- [ ] Universal binary (`aarch64` + `x86_64`) unless there is a stated reason not to.
- [ ] **Signed and notarized.** The owner holds a `Developer ID Application: Ahmet Yusuf
      BİRİNCİ (Z678QXV882)` certificate with its private key — the right kind for
      distribution outside the App Store. Upstream's `signed-macos-canary.yml` signs through
      Block's internal S3/role infrastructure and is **not** a model for this; write the
      standard Tauri path, which reads `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`,
      `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID` from the
      environment.
- [ ] **Never handle the private key.** Exporting the `.p12` and setting the repository
      secrets is the owner's action, not an agent's — no agent reads, copies, prints or

- [ ] **Degrade honestly when the secrets are absent.** A build with no certificate must
      still produce a working unsigned `.dmg` and must **say in the release notes that it is

      Whichever path a run took must be visible from the release itself.
- [ ] The workflow is fork-owned but lives at `.github/workflows/` — an upstream path.
      It needs a `vingilot/seams.yaml` entry saying so.
- [ ] It must not run upstream's release automation by accident: check what else triggers on
      tags in this repo (`auto-tag-on-release-pr-merge.yml`, `release.yml`) and make sure a

- [ ] Cheap proof without burning runner minutes: validate the workflow file, and dry-run the

## Global Constraints

- **`rm -rf` forbidden**, any path, including test teardown and generated icon sets.
- **Resource budget:** `df -h /System/Volumes/Data` before any build; **stop below 20 GiB**.
  A release build is authorised for this branch — the owner asked for a distributable app —
  but never two heavy builds at once, and never while another workflow is building.
- **Never launch the app or any GUI.** The built artifact is produced, not run; the owner
  installs and opens it.
- **The owner's tmux sessions live on the default socket** — never touch it. Never kill a
  process you did not start. **Nothing outside this repo.**
- **Do not change the repository's visibility, create releases, or push tags.** Publishing is
  the owner's action, not an agent's.
- Never `git add -A`; never amend, rebase, or force-push. Trailers `Signed-off-by` then
  `Co-authored-by`; `git commit -F`, never `-s`.
- Island-first; anything outside `desktop/src/features/runs/**` and `vingilot_*/**` needs a
  `vingilot/seams.yaml` entry with a true, specific reason. Tasks 1 and 3 will need several.
- **An empty read is "no answer", never "nothing there."**
- **A test must be able to fail** — prove each new test red by breaking what it guards.

## Self-Review

**Riskiest:** the bundle identifier. Changing it silently moves the app's data directory, and
the owner has real work in this app — terminal layouts, notes, plans, and agent keys that may
live in the keychain under the old identity. The failure mode is not a crash; it is an app
that opens looking brand new. Whatever is decided must be stated plainly before it ships.

**Most likely to be got wrong quietly:** the light theme. Both the mark and the animation come
from white-on-dark artwork, and every quick path — ship the white bitmap, key the glow in —
looks perfect on the dark theme the implementer is developing against and wrong on the other
one. Check both, every time, and prefer the tinting mechanism the app already has.
